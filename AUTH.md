# Доступ в Mamla по приглашениям

Авторизация ограничивает доступ к сервису целиком. Любой допущенный пользователь
может входить в любую комнату, если знает её ID. Отдельных прав на комнаты нет.

## Включение за Envoy

Соберите сервер командой `make server`. В терминале сервера:

```sh
export AUTH_FILE="$HOME/.local/share/mamla/auth.json"
export PUBLIC_URL="https://mamla.io"
ADDR=127.0.0.1:8080 ./dist/mamla-linux-amd64
```

Замените домен на свой; для ARM64 используйте соответствующий бинарник.
При заданном `AUTH_FILE` сервер создаст приватный файл и потребует доступ
для всех API звонка, включая ICE-конфигурацию и поток событий.
Без `AUTH_FILE` сохраняется прежний открытый режим для локального POC.
Выбранный режим печатается при запуске и виден в `/api/auth/status`.

`PUBLIC_URL` нужен CLI для создания приглашений; это HTTPS-origin без пути,
query и fragment. Серверу непосредственно за Envoy сертификат не нужен:
браузер видит HTTPS Envoy, cookie имеет флаг Secure, а внутренний upstream может
оставаться HTTP. Не открывайте upstream-порт Mamla в публичную сеть.

Envoy должен сохранять исходный `Host`/`:authority`, `Cookie`, `Set-Cookie`,
`Authorization` и `X-Mamla-Key`. Для `/api/events` нужны streaming без буферизации,
`timeout: 0s` и idle timeout больше 15 секунд. На публичном listener настройте
rate limiting, особенно для `/api/auth/login` и `/api/auth/accept`.
Не включайте запись тел запросов и секретных заголовков в access log.

В systemd/контейнере задайте `AUTH_FILE` постоянно, под тем же пользователем,
что запускает сервер и CLI. Файл должен находиться на локальном постоянном диске
или volume и иметь права `0600`; новый каталог создаётся с `0700`.
Храните резервную копию файла: без него прежние личные ключи не распознаются.
Это хранилище для одного экземпляра Mamla, не распределённая база.

## Пригласить человека

В другом терминале на том же сервере укажите те же переменные:

```sh
export AUTH_FILE="$HOME/.local/share/mamla/auth.json"
export PUBLIC_URL="https://mamla.io"
./dist/mamla-linux-amd64 invite create friend --expires 24h
```

Команда выдаёт одну ссылку вида `https://mamla.io/#invite=…`.
Передайте её приглашённому по доверенному каналу. До использования эта ссылка —
секрет: кто первым подтвердит её принятие, тот и получит доступ.
По умолчанию срок — 24 часа, максимум — 720 часов. Для себя создайте такое же
приглашение с собственным названием доступа.

Имя `friend` — метка для управления доступом. Она не обязана совпадать с ником,
который человек вводит в комнате. Новое активное приглашение для той же метки
или ещё одного активного пользователя с этой меткой создать нельзя.

Приглашение находится во fragment URL: браузер не передаёт его в HTTP-запросе
страницы или Referer. JS сразу убирает fragment из адресной строки.
Обычный переход и предпросмотр мессенджера не расходуют приглашение.

## Что видит приглашённый

1. Открывает ссылку и нажимает «Принять приглашение».
2. Браузер создаёт криптографически случайный 256-битный личный ключ.
3. При POST-запросе сервер атомарно гасит приглашение, сохраняет хеш ключа
   и создаёт браузерную сессию на семь дней.
4. Человек скачивает ключ или сохраняет в менеджере паролей, затем скрывает его
   кнопкой «Ключ сохранён — скрыть». Сервер не может показать ключ повторно.
5. Открывает ссылку нужной комнаты или создаёт свою и делится её ссылкой.

Ключ не сохраняется в localStorage и не попадает в URL. Браузерная сессия
использует cookie `__Host-mamla_auth` с Secure, HttpOnly, SameSite=Lax и Path=/.
После выхода или истечения семи дней можно снова войти по сохранённому ключу.
У самого ключа нет срока действия: он работает до отзыва доступа.

При потере ответа во время принятия приглашение могло уже погаситься. Созданный
ключ остаётся на странице: сохраните его и нажмите «Войти с этим ключом».
Не закрывайте страницу до сохранения. Если ключ утрачен, администратор отзывает
старый доступ и выдаёт новое приглашение.

Владелец сервера в обычном интерфейсе управления не получает личный ключ.
Ключ всё же передаётся серверу по HTTPS для проверки и хеширования — это не
схема защиты от администратора, способного менять сервер или перехватывать его память.

## Linux-клиент

Примите приглашение в браузере и скопируйте личный ключ в поле
«Личный ключ доступа» Linux-клиента. Он отправляется заголовком `X-Mamla-Key`;
существующий `Authorization: Bearer` остаётся токеном комнаты.
Перенаправления HTTP в нативном клиенте запрещены, чтобы ключ не ушёл другому
upstream. Используйте сразу правильный HTTPS-адрес. Ключ хранится только в памяти
окна; системное хранилище секретов и принятие приглашений внутри GTK пока не реализованы.

Если скачали ключ в файл, ограничьте доступ к нему (`chmod 600 путь-к-файлу`)
или перенесите в менеджер паролей. На публичном сервере используйте нормальную
проверку TLS: тестовая кнопка обхода сертификата позволяет перехватить ключ.

## Управление и отзыв

```sh
./dist/mamla-linux-amd64 access list
./dist/mamla-linux-amd64 access revoke friend
```

Обе команды требуют того же `AUTH_FILE`. Список содержит ID, метки и состояния,
но не секреты и не их хеши. Отзывать можно по метке или ID. Отзыв метки гасит
также её неиспользованные приглашения и все выданные пользователю сессии.
Следующий API-запрос отклоняется сразу, активные SSE-соединения проверяются
раз в 15 секунд и закрываются; клиенты останавливают звонок.

Административных HTTP-методов создания приглашений нет: операции доступны
только через CLI с правами на приватный файл. CLI и сервер синхронизируют изменения
через файловую блокировку, запись выполняется атомарной заменой.
В файле лежат SHA-256-хеши случайных ключей, приглашений и сессионных токенов;
пароли людей здесь не используются.

## Проверки

Для JS-тестов нужен Node.js 22+; серверу в работе Node.js не требуется.

```sh
go test -race ./...
node --test tests/auth-ui.test.mjs
cd linux-client
cargo test --locked
```

Для группового интеграционного теста с авторизацией можно передать
`MAMLA_TEST_SERVER` и `MAMLA_TEST_KEY` в окружении процесса, не в URL:

```sh
cargo test three_clients_join_mute_and_leave -- --ignored
```

Go-тесты проверяют одноразовость при одновременных запросах, истечение срока,
cookie, вход по ключу, изоляцию чужих сессий, отзыв с закрытием SSE, CSRF,
приватность файла и CLI. JS-тесты с DOM-заглушками проверяют отсутствие принятия
при обычном переходе и восстановление после потерянного ответа; они не заменяют
проверку внешнего вида в настоящем браузере.

# Mamla

Минималистичный групповой voice chat. Сервер на Go без внешних зависимостей,
браузерный POC на обычном JavaScript. Интерфейс встроен в бинарник через `go:embed`.

## Запуск

Нужен Go 1.23 или новее.

```sh
go run .
```

Откройте http://localhost:8080, введите имя и разрешите микрофон.
Нажмите «Копировать ссылку» и откройте её в другом браузере или профиле браузера
на том же компьютере. По умолчанию сервер слушает только loopback.
Для проверки акустики используйте наушники; две вкладки на одном устройстве
могут создавать эхо. Новая главная страница создаёт случайный ID комнаты.

```sh
go test -race ./...
go build -o mamla .
```

Статический Linux-бинарник сервера (нужны Go и Make):

```sh
make server                  # dist/mamla-linux-amd64 (также цель по умолчанию)
make server GOARCH=arm64     # dist/mamla-linux-arm64
```

Сборка использует `CGO_ENABLED=0`, не требует libc на целевой Linux-машине
и работает в том числе при кросс-компиляции с macOS. HTML/CSS/JS уже встроены
в бинарник; каталог `web` переносить не нужно. Это цель только для Go-сервера,
нативный Rust/GTK-клиент собирается отдельно.

Запуск на целевом Linux-хосте:

```sh
ADDR=0.0.0.0:8080 ./dist/mamla-linux-amd64
```

Путь результата можно переопределить: `make server OUTPUT=./mamla`.

Нативный Linux-клиент собирается отдельной целью на Linux:

```sh
make client                  # dist/mamla-client
./dist/mamla-client
```

Зависимости GTK4/GStreamer/PipeWire и настройка noise gate описаны
в [инструкции клиента](linux-client/README.md). Клиент динамический; в отличие
от сервера, его библиотеки и плагины нужны и на машине запуска.

## Подключение с другого компьютера

Для доступа по сети запустите `ADDR=0.0.0.0:8080 go run .` и поставьте перед
сервером HTTPS reverse proxy (например Caddy). В браузере микрофон доступен
через **HTTPS** или localhost: `http://192.168.x.x:8080` для этого не подходит.
У reverse proxy нужно отключить буферизацию SSE и разрешить долгие соединения.
Для разговора участники открывают одну и ту же HTTPS-ссылку комнаты.

Сервер также умеет обслуживать HTTPS самостоятельно, без reverse proxy:

```sh
ADDR=0.0.0.0:8443 TLS_CERT_FILE=/path/to/cert.pem TLS_KEY_FILE=/path/to/key.pem go run .
```

Сертификат должен покрывать IP или домен, по которому подключается клиент.
Для локального POC допустим самоподписанный сертификат, но браузер покажет
предупреждение о доверии: его проверку и решение о доверии выполняет пользователь.
Устройства с запретом локальных исключений потребуют доверенного сертификата.
Не отключайте проверку сертификатов для браузера целиком.

Ошибка `Load failed` сама по себе не доказывает проблему сертификата.
Сначала проверьте тот же адрес с путём `/api/config` и запрос `/api/events`
в Network браузера. Если подтверждена проблема доверия в Safari,
добавьте **только публичный** `cert.pem` в «Связку ключей»
на Mac и явно разрешите доверие этому сертификату для SSL, затем заново откройте
страницу. Закрытый `key.pem` не переносится. Альтернатива — сертификат доверенного
CA или явный тестовый режим подключения в нативном Linux-клиенте.

По умолчанию настроен публичный Google STUN. Для некоторых NAT/корпоративных
сетей требуется **TURN**: без него передача голоса через интернет не гарантирована.
Настройка через `ICE_SERVERS` — JSON-массив стандартных `RTCIceServer`:

```sh
ICE_SERVERS='[{"urls":"stun:stun.l.google.com:19302"},{"urls":"turn:turn.example.org:3478","username":"temporary-user","credential":"temporary-password"}]' go run .
```

В примере — заглушки. В реальном развёртывании используйте короткоживущие
TURN-учётные данные: `/api/config` отдаёт ICE-настройки браузерам.

## Что работает

- Комнаты по ссылке, до 6 участников, без регистрации.
- Голос WebRTC, выключение микрофона, индикация говорящего.
- Список участников, уведомления о входе/выходе, освобождение микрофона при выходе.
- Сообщения об отказе доступа к микрофону, потере сигналинга и ошибках соединения.
- Отдельный HTTP/JSON + SSE протокол для будущего Linux-клиента.

## Архитектура и границы POC

Go обслуживает интерфейс и сигналинг. Аудио идёт между клиентами по WebRTC
(DTLS-SRTP); сервер сигналинга его не принимает и не записывает. При использовании
TURN медиатрафик проходит через relay в зашифрованном виде.

Топология — полный mesh: каждому клиенту нужно N−1 соединений. Лимит 6 — ограничение
этого POC, а не обещание качества для любой сети. Для больших комнат стоит выбрать
SFU. Всё состояние хранится в памяти одного процесса и теряется при перезапуске.
Нет авторизации пользователей, модерации, защиты от массовых запросов и автоматического
восстановления сессии. Ссылка даёт доступ в комнату. Это POC для доверенной компании.
Демонстрация в браузере не доказывает стабильную работу в фоне или при блокировке экрана.

Для Linux есть отдельный [нативный Rust-клиент](linux-client/README.md):
GTK4, GStreamer WebRTC/Opus и прямой ввод/вывод через PipeWire.
Бинарник `mamla` в корне — **сервер с веб-клиентом**; Rust GUI собирается отдельно.

## Протокол v1

Все запросы идут на один origin. JSON UTF-8. Ошибка: `{"error":"сообщение"}`.
Токен сессии передаётся заголовком `Authorization: Bearer <token>`, а не в URL.

| Запрос | Тело / ответ |
| --- | --- |
| `GET /api/config` | `{iceServers: [...], roomLimit: 6}` |
| `POST /api/join` | `{room, name}` → 201 `{id, token}`; 409 если комната заполнена |
| `GET /api/events` | Авторизованный SSE-поток; открыть в течение 30 секунд после join |
| `POST /api/signal` | `{to: participantId, type: "offer" / "answer" / "ice", data: object}` → 204 |
| `POST /api/mute` | `{muted: boolean}` → 204 |
| `POST /api/leave` | Без тела → 204; токен аннулируется |

Комната: `[a-z0-9][a-z0-9-]{0,63}`, имя: 1–32 Unicode-символа после trim.
Сообщение ограничено 64 КиБ. Участник: `{id, name, muted}`.
Для каждой сессии допускается один SSE-поток. Формат фрейма:

```text
data: {"type":"ready","data":{"peers":[]}}

```

События:

- `ready`: `{peers: Participant[]}` — уже подключённые участники; новый клиент
  создаёт WebRTC offer каждому из них. Только новичок инициирует переговоры.
- `peer-joined` / `peer-updated`: `Participant`.
- `peer-left`: `{id}`.
- `signal`: `{from, type, data}`. `offer`/`answer` используют `RTCSessionDescriptionInit`,
  `ice` — `RTCIceCandidateInit`. ICE, пришедший до remote SDP, нужно буферизовать.

Сервер раз в 15 секунд отправляет SSE-комментарий `: ping`. Разрыв потока удаляет
участника и уведомляет остальных. Для повторного подключения нужен новый join.
Сигналы пересылаются только внутри комнаты, token не раскрывается другим участникам.
